# Воркфлоу: Предложения + агент-валидатор (RW-1 — RW-6)

Описание того, как реально работает автоматизация «Предложение → валидация агентом → Решение», для тех, кто будет её эксплуатировать или дорабатывать. Проверено на проде 19–20 сентября 2026 (см. раздел «Приёмка» внизу).

## Зачем это существует

До этой автоматизации путь идеи был двухступенчатым: заметка в Playground → сразу Epic или Решение, минуя проверку на соответствие текущему плану. Предложения — промежуточное состояние: сырая идея попадает в очередь, агент сверяет её с канонными документами (Product Definition, MVP Epic Map, Technical Architecture Plan) и текущими Epic/Решениями, и только после этого человек решает, что с ней делать. Агент не имеет права сам менять статус — только даёт рекомендацию.

## Жизненный цикл предложения

```
Playground-заметка ──(RW-5, опционально)──▶
                                            │
                                            ▼
                                         Новое
                                            │  человек переводит в «На валидации»
                                            ▼
                                    На валидации ──▶ [агент-валидатор] ──▶ verdict_* записан
                                            │
                     ┌──────────────────────┼───────────────────────────┐
                     ▼                      ▼                           ▼
                 Одобрено            Заблокирован:              Отклонено /
           (RW-4: «Оформить      продукт / дизайн /            Нужен прототип
            как Решение» →        технически
            новая запись в
            Решениях, decision_id
            проставляется автоматически)
```

Статусы (`proposals.status`): `new` → `validating` → `approved` / `rejected` / `blocked_product` / `blocked_design` / `blocked_technical` / `needs_prototype`. Переходы делает человек кликом на бейдж статуса — это единственное место, где меняется `status`.

## Шаг 1 — создание предложения

Два входа:

1. **Напрямую** на `/proposals` → «+ Новое предложение»: название, описание, кто предложил, владелец (опционально), привязка к Epic (опционально).
2. **Из Playground** (RW-5): на странице заметки (`/playground/[id]`) есть ссылка «Оформить как Предложение →». Она ведёт на `/proposals?title=...&description=...&sourceNoteId=<note-id>` — форма открывается предзаполненной, а после сохранения `source_note_id` пишется в новую запись как обратная ссылка на заметку.

Код: `ProposalForm.tsx` берёт `initialSourceNoteId` из query-параметра и всегда передаёт его в `onSubmit`, даже если поле не редактировалось руками.

## Шаг 2 — «На валидации» запускает агента

Клик по бейджу статуса → «На валидации» в `ProposalStatusControl.tsx` вызывает `updateStatus(id, "validating")` в `useProposals.ts`. Эта функция:

1. Пишет `status = "validating"` в БД (сразу, оптимистично).
2. Если новый статус — именно `"validating"`, дополнительно дёргает `POST /api/proposals/validate` с `{ proposalId }`.
3. Пока запрос летит, id предложения лежит в `validatingIds` → карточка показывает «Агент проверяет предложение…».
4. Ошибка (сеть, отсутствие ключа, парсинг ответа) пишется в `verdict_error` и показывается прямо на карточке — отдельного лога смотреть не нужно.

Важно: агент **не блокирует и не меняет** статус — он только пишет в `verdict`, `verdict_rationale`, `verdict_references`, `verdict_owner`, `verdict_at`. Даже если агент недоступен, предложение спокойно остаётся в «На валидации», и статус можно сменить вручную.

## Шаг 3 — что делает агент (`src/app/api/proposals/validate/route.ts`)

1. Читает само предложение из БД.
2. Параллельно тянет: реестр baseline-документов (таблица `documents`, `is_baseline = true`), список Epic (title/description/priority/status), список Решений (type/title/description/status).
3. Для каждого baseline-документа резолвит GitHub-ссылку в локальный файл внутри `docs/` (регэксп на `/docs/<файл>.md`) и читает его с диска — так агент не зависит от отдельного сетевого похода в GitHub API (который у `/development`-виджета и так иногда отдаёт 401).
4. Собирает system-промпт: канонические документы (с `cache_control: ephemeral` — это то самое prompt caching) + текущие Epic + текущие Решения + строгий формат JSON-ответа.
5. Стучится в `POST {ANTHROPIC_BASE_URL}/v1/messages` с моделью `claude-sonnet-5`.
6. Ищет в ответе **первый блок с `type: "text"`** среди `content[]` — это важно, потому что при extended thinking первым блоком идёт пустой `thinking`, и `content[0]` — не то, что нужно (это баг, который был здесь до 20.09.2026, см. коммит `8796951`).
7. Вынимает JSON из текста (`extractJson`, понимает и ```json-обёртку, и голый JSON) и пишет `verdict_*` в БД.

Вердикты: `aligned` / `product_issue` / `design_issue` / `technical_decision` / `needs_prototype` / `out_of_scope`, плюс `recommended_owner` (одна из ролей RW-2) и `references` — конкретные разделы документов, а не общие фразы.

## Шаг 4 — владелец и роли (RW-2)

`src/lib/owners.ts` — единый словарь ролей, используется в Epic, Решениях и Предложениях: `analysis`, `project`, `testing`, `development`, `techlead` (пять дисциплин канбана) плюс `founder`, `game_design`, `product_manager`, `product_lead` (реальные accountable-роли для вердиктов агента). Владельца можно выставить вручную в любой момент через выпадающий список на карточке — это прямой `UPDATE proposals SET owner = ...`, не завязано на вердикт.

## Шаг 5 — оформление в Решение (RW-4)

Кнопка «Оформить как Решение» на карточке (пока `decision_id` пуст) вызывает `promoteToDecision()` в `useProposals.ts`:

1. Создаёт запись в `decisions`: `type: "decision"`, `status: "active"` («Решение» / «Действует»), `title`/`description` копируются из предложения, вердикт агента (`rationale` + `references`) дописывается в конец описания, `proposal_id` — обратная ссылка.
2. Обновляет само предложение: `decision_id` = id новой записи, `status = "approved"`.

Кнопка не принимает никаких параметров с экрана — это всегда именно «Решение», а не «Открытый вопрос» или «Риск» (до 20.09.2026 был баг: код по умолчанию создавал `open_question`/`needs_investigation`, из-за чего кнопка обманывала своим названием — исправлено в коммите `1a8ee9a`). Если нужен другой тип записи для конкретного предложения — это делается вручную на `/decisions` после создания.

## Конфигурация (обязательно для RW-3)

В Vercel → Project Settings → Environment Variables (Production):

| Переменная | Назначение |
|---|---|
| `ANTHROPIC_API_KEY` | ключ кастомного прокси. Без него route возвращает 501 и понятную ошибку прямо на карточке, ничего больше не ломается. |
| `ANTHROPIC_BASE_URL` | база прокси, без завершающего `/v1/messages` — код сам его достраивает. Правильное значение: `https://ai.starimg.ru/`. |

После изменения переменных **обязателен редеплой** — Vercel запекает env в сборку serverless-функций, простое сохранение переменной в дашборде на уже накаченный деплой не действует.

`.env.local` — тот же набор для локальной разработки; не должен попадать в git ни в каком виде (даже в документации) — один раз уже случайно закоммитили реальный ключ в `RW_IMPLEMENTATION_STATUS.md`, пришлось редактировать файл и ротировать ключ.

## Известные ограничения (осознанные, не баги)

- Агент никогда не трогает `status` — правило, не забытая фича.
- Реестр документов читается с диска на момент вызова; если `docs/*.md` устарели относительно реального плана, вердикт будет опираться на устаревшие данные — это операционный процесс (обновлять доки), не техническая проблема.
- Prompt caching даёт экономию только начиная со второго вызова подряд с тем же system-промптом; первый вызов после деплоя или после паузы — дороже и чуть медленнее.
- Реалтайм-подписки на `proposals`/`decisions`/`epics` — три независимых хука, у каждого свой `loading`. На практике это означает, что сразу после мутации карточка иногда на секунду-две показывает неактуальную производную (например, кнопку «Оформить как Решение» вместо уже готовой ссылки «Оформлено в Решения: …»), пока не подтянутся связанные списки. Само действие уже выполнено — это только визуальная гонка загрузки, обновление страницы или пара секунд ожидания её убирают.

## Приёмка (что реально проверено на проде)

Все пункты ниже пройдены на `rubezhweb.vercel.app` 19–20.09.2026, включая полный цикл RW-6 с настоящим текстом из `/marketing-assessment» («Технический спайк: custom combat vs Epic Fight» → вердикт «Вне MVP-скоупа» со ссылками на Product Definition v4 → оформлено в Решение) и сквозную проверку `source_note_id` через прямой REST-запрос к Supabase (значение в БД совпало с id заметки Playground).

- RW-1 — сущность и раздел интерфейса работают на проде.
- RW-2 — роли Founder/Game Design/Product Manager/Product Lead доступны в выпадающем списке и сохраняются.
- RW-3 — агент вызывается, пишет структурированный вердикт с обоснованием и ссылками на конкретные разделы документов.
- RW-4 — промоушен создаёт именно «Решение»/«Действует» с обратной ссылкой на предложение.
- RW-5 — путь из Playground предзаполняет форму и сохраняет `source_note_id`.
- RW-6 — сквозной прогон на реальном контенте маркетингового отчёта пройден.

По пути найдены и исправлены три продовых бага (неверный `ANTHROPIC_BASE_URL`/отсутствующий `ANTHROPIC_API_KEY` — конфигурация; неправильный разбор content-блоков ответа модели — коммит `8796951`; неверный тип записи при промоушене — коммит `1a8ee9a`).
