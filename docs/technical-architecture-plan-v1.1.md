# TECHNICAL ARCHITECTURE & IMPLEMENTATION PLAN v1.0 — RUBEZH

Источники: RUBEZH Product Definition v4 (12.09.2026), MVP Epic Map v2.0 (на основе PD v4, 12.09.2026), GAME DESIGN REVIEW: Epic Decomposition v2.0 (Game Designer, 12.09.2026). Роль: Technical Lead / Technical Architect. Отвечаю на HOW; не переопределяю WHAT (Product) и GAMEPLAY (Game Design) — где технический анализ упирается в их решение, помечаю как PRODUCT ISSUE / DESIGN ISSUE и передаю обратно.

## 1. Executive Summary

Проект технически реализуем силами небольшой команды на выбранном стеке (NeoForge 1.21.1) без отдельного backend/микросервисной инфраструктуры — MVP осознанно ограничен одиночным/малым-кооп опытом (2–4 игрока), постоянный сервер и экономика в Later. Это снимает большую часть архитектурного риска, который обычно ломает маленькие модовые команды.

Главные технические развилки, которые определяют, можно ли начинать полномасштабную разработку:

Защитный инструмент боя не выбран (блок/парирование/позиционирование) — блокирует полную реализацию EPIC-002. Это Design decision, не мой — но я показываю ниже, что часть EPIC-002 (боевой state machine, стамина/пойз) можно строить уже сейчас, не дожидаясь этого решения.

Технический спайк сетевой синхронизации боя (EPIC-003, H6) не пройден — go/no-go для всей боевой архитектуры на кооп-масштабе.

Архитектура survival-системы не решена (кастом vs Create/Mekanism/AE2) — прямой риск конфликта с глубокими хуками кастомного боевого мода.

Два пробела, найденных Game Designer’ом (владение оружием между EPIC-002/005, отсутствие failure-state механики), — design-вопросы по сути, но у обоих есть чисто техническое решение, которое можно принять прямо сейчас, не дожидаясь Founder.

Итоговый статус: NEEDS PROTOTYPE для боевого/сетевого/survival ядра, TECHNICALLY READY WITH RISKS для контентных треков (регион, лор), которые можно начинать параллельно уже сейчас.

## 2. Technical Reconstruction

Known: платформа NeoForge 1.21.1 (Founder decision, порт на 1.20.1 — опционально позже); вторичный стек Create, FTB Quests, FTB Teams, Mekanism, AE2 подтверждён официальными релизами на 1.21.1; Ad Astra/MineColonies — не подтверждены, но relevant только для S2+/космос, вне MVP. Команда — волонтёрская, устойчивый темп 4–6 ч/день на человека, ~2 человека на критичную специализацию (включая 2 специалистов на анимацию/3D), bus factor — явно зафиксированный риск с митигацией через документирование (Product Pillar №9). MVP — сессионный одиночный/малый-кооп (2–4 игрока) опыт, без персистентной экономики и without dedicated backend.

Это принципиально меняет архитектурные ставки по сравнению с любой версией продукта, где сервер был MVP-пиларом: не нужна выделенная backend-команда, DevOps на постоянной основе или distributed-инфраструктура. Авторитетность игрового состояния может жить в самом Minecraft-сервере (интегрированный сервер одиночной игры или dedicated LAN/hosted-сервер для сессии друзей), без отдельного сервиса.

## 4. High-Level Architecture

Client: Minecraft client + кастомные моды — рендер и анимации боевых состояний (weapon arts, телеграфы атак), UI билдов/лора, client-side prediction для отзывчивости тайминг-боя.

Server: NeoForge server (интегрированный сервер одиночной игры или dedicated/hosted для сессии 2–4 друзей) — авторитетное разрешение урона/пойза/стамины, AI кастомных мобов, генерация трофеев/лута, персистентные данные игрока, survival-состояние.

Shared: data-driven определения (архетипы оружия, статы мобов, узлы дерева способностей, loot-таблицы) — загружаются на обеих сторонах для консистентного client-side prediction и рендера.

Внешние зависимости (подтверждены на NeoForge 1.21.1): Create, FTB Quests, FTB Teams, Mekanism, AE2. Это не просто “совместимый стек” — это конкретные технические решения-кандидаты:

FTB Teams — прямой кандидат на техническую основу EPIC-009 (Team Formation & Access) вместо кастомной permission-системы с нуля. Это ровно тот случай из принципа “не переинжиниринг” (раздел 27): если FTB Teams покрывает нужный минимум допусков на 2–4 игроках, EPIC-009 сжимается до конфигурации/интеграции, а не нового слоя инфраструктуры.

Create / Mekanism / AE2 — кандидаты на техническую основу производственных цепочек в EPIC-006, но с реальным риском конфликта с глубокими хуками кастомного боевого мода (mixin-конфликты на Forge/NeoForge — известный класс проблем). Требует спайка (см. §12).

FTB Quests — потенциальный технический носитель для лор-прослойки (EPIC-007): quest-подобная структура для триггеров environmental storytelling снижает объём кастомного UI/tracking, который иначе пришлось бы писать с нуля.

Backend/база данных отдельным сервисом не нужны на этом масштабе — персистентность живёт в стандартном player-data слое Minecraft/NeoForge (NBT/capabilities).

## 6. Core Technical Systems — разбор с учётом ревью Game Designer’а

### 6.1 Combat Core (EPIC-002)

Компоненты: CombatStateMachine (фазы: windup/active/recovery/interrupt — не зависят от того, какой защитный инструмент выберет Design), StaminaSystem, PoiseSystem, WeaponArchetypeRegistry, DefensiveToolSystem (TBD).

Ключевой технический вывод: CombatStateMachine, StaminaSystem, PoiseSystem и WeaponArchetypeRegistry не заблокированы решением о защитном инструменте — это общий фундамент вне зависимости от того, будет это блок, парирование или позиционирование. Заблокирован только сам DefensiveToolSystem. Это значит, что Foundation-часть EPIC-002 можно начинать разрабатывать прямо сейчас, параллельно с тем, как Founder/Game Design решают открытый вопрос (раздел 19.20 Product Definition) — реальный технический прогресс не должен стоять в очереди за одним design-решением.

TECHNICAL DECISION (предложение, отвечает на находку 2.1 ревью Game Designer’а — разделение владения оружием): развести модель данных на WeaponArchetype (code+config, фиксированный набор движков/moveset под тип оружия — владелец EPIC-002) и WeaponInstance (data-driven, персистентный, хранит тир/статы/апгрейды — владелец EPIC-005), где WeaponInstance ссылается на WeaponArchetype. Это прямая техническая реализация границы, предложенной Game Designer’ом. Решение малорискованное и обратимое (§Decision Log ниже) — рекомендую принять его как рабочий интерфейс уже сейчас, не дожидаясь формального утверждения PM, чтобы не блокировать декомпозицию EPIC-005.

### 6.2 Combat Network Sync (EPIC-003)

Целевой масштаб — 2–4 игрока (LAN/hosted-сессия), не MMO — это существенно снижает инженерную сложность: не нужны area-of-interest management, шардинг, региональные сервера. Большая часть сетевой синхронизации в Minecraft уже решена ванильным протоколом (entity tracking, attribute sync); кастомный риск сосредоточен конкретно в: (а) согласовании тайминга hit-confirmation между клиентом и сервером при реальном пинге (lag-compensation для боевых окон), (б) корректной репликации переходов состояния пойза/стагера.

Рекомендуемый scope спайка — не “общий netcode”, а прицельно: hit-confirmation + poise-state под реалистичным пингом на 2–4 участниках. Это уже, чем формулировка в Epic Map, и должно ускорить получение go/no-go по H6.

### 6.3 Custom Mobs (EPIC-004)

AI (server) должен телеграфировать атаки способом, совместимым с итоговым защитным инструментом игрока — то есть полная реализация действительно зависит от решения по §6.1. Но behavior tree и базовая AI-логика мобов можно прототипировать против заглушки боевой системы уже сейчас, чтобы не простаивать всей веткой EPIC-004 целиком.

### 6.4 Build & Ability Progression (EPIC-005)

При принятии предложения из §6.1 (WeaponArchetype/WeaponInstance) декомпозиция EPIC-005 разблокируется независимо от финального решения Founder по защитному инструменту — прогрессия оружия не зависит от того, чем именно игрок защищается.

### 6.5 Survival & Crafting Loop (EPIC-006)

Needs Investigation (соответствует Technical Lead Review в самой Epic Map, раздел 9): кастомная реализация голода/добычи/производства vs. интеграция с Create/Mekanism/AE2. Рекомендуемый спайк — см. §12, Spike 2. Компонентно: ResourceGatheringSystem, ProductionChainSystem (или делегирование Create/Mekanism), HungerSystem (кастом или ваниль), TrophyToGearBridge.

TECHNICAL DECISION (отвечает на находку 2.2 ревью Game Designer’а — Trophy→Gear физически не там, где принадлежит): независимо от того, в какой Feature-группе продуктово окажется “апгрейд от трофея”, технически развожу это так: EPIC-004 производит объект трофея как данные; логику “потратить трофей → улучшить снаряжение” держит компонент, принадлежащий Build/Progression data store (владелец EPIC-005), а не Survival-система. EPIC-006 поставляет только сырые survival-ресурсы (еда/добыча/производство) и не содержит логику апгрейда снаряжения. Это техническое разделение стоит внедрить в коде уже сейчас, вне зависимости от финального продуктового решения о Feature-группировке.

### 6.6 Failure State — отсутствующий владелец (соответствует находке 2.3 ревью Game Designer’а, самой серьёзной)

Ни один Epic не определяет механику потерь при смерти/провале — Game Designer верно называет это design-пробелом. Но с технической стороны это не только design-вопрос: даже когда Founder/Design решат ЧТО теряется, инженерной команде всё равно нужен механизм КАК это происходит безопасно.

Уточнение (снимает overclaim предыдущей версии этого документа): утверждение «механизм не зависит от содержания потерь» верно только для одного семейства решений, а не для любого выбора Design. Есть как минимум два технически разных варианта:

Tier A — Rollback / outright loss (например: при смерти безвозвратно теряется X% валюты/трофеев). Технически это чистая транзакция над персистентными данными игрока — snapshot/commit/rollback: снять состояние перед риск-событием, закоммитить при успехе, откатить или частично применить при провале. Этот компонент действительно не зависит от содержания потерь — механизм одинаков, теряет ли игрок 10% валюты или конкретный трофей, потому что он работает с данными игрока, а не с миром.

Tier B — Bloodstain-style recoverable drop (например: при смерти игрок роняет трофеи/валюту как объект в точке смерти, который можно вернуть, а повторная смерть до возврата — окончательная потеря; паттерн, знакомый по Dark Souls). Это не другой параметр той же транзакции, а отдельный технический компонент: персистентный world-object (не просто запись в player-данных), позиция дропа, TTL/логика деспавна, обработка подбора (тем же игроком или напарником в коопе), поведение при нескольких смертях подряд (стекование дропов или замена) и конкурентный доступ в кооп-сессии (два игрока претендуют на один дроп одновременно). Ничего из этого не покрывается Tier A.

Итог: генерализация «не зависит от содержания потерь» справедлива только внутри Tier A. Если Design выберет что-то в духе Tier B, это отдельный, не переиспользуемый из Tier A объём работы, который нельзя спроектировать заранее, не зная, что выбрано.

TECHNICAL DECISION: строить Tier A (обобщённый rollback-транзакционный слой) сейчас, не дожидаясь решения Design — он полезен при любом исходе как минимум как основа для отмены незавершённых риск-событий и защиты от дюпа. Tier B, если он потребуется, — отдельная техническая задача, которую нельзя начинать до design-решения и нельзя закрыть тем же Spike 3 (см. §12).

DESIGN ISSUE (передаю обратно, не решаю): что конкретно теряет игрок — вопрос Founder/Game Design, уже корректно поставлен как Blocking в ревью Game Designer’а (раздел 4) и должен быть закрыт до Feature-декомпозиции EPIC-002/006. От этого решения зависит не только геймдизайн, но и то, добавляется ли в объём работы отдельный Tier B-компонент.

### 6.7 Team Formation & Access (EPIC-009)

TECHNICAL DECISION (предложение): оценить FTB Teams (подтверждённая зависимость стека) как техническую основу вместо кастомной permission-системы. Если FTB Teams покрывает “минимальные допуски на совместные активности” для 2–4 игроков, EPIC-009 технически сжимается до интеграции/конфигурации.

DESIGN ISSUE (не решаю, только фиксирую техническую сторону): ревью Game Designer’а (находка 2.4) справедливо указывает, что Scope EPIC-009 не описывает ни одного player decision — “минимальные допуски” не отвечает на вопрос, что именно регулируется (делёж лута? право сноса построек?). Это вопрос к Founder/Game Design независимо от того, что технической реализацией может стать готовый мод — техническое решение не снимает необходимость ответить на вопрос “зачем” this Epic вообще существует на масштабе 2–4 без персистентной экономики.

### 6.8 Coop Multiplayer Foundation (EPIC-010)

Технически ключевое уточнение: ванильный Minecraft уже поддерживает N игроков в одном мире/сервере — “фундамент” здесь не про новую сессионную инфраструктуру, а про то, чтобы кастомные системы (боевая синхронизация EPIC-003, survival-состояние) корректно работали при конкурентном доступе 2–4 игроков (одновременная работа у одной крафт-станции, совместный бой с одним мобом и т.д.). Рекомендую явно сузить scope до “проверка корректности существующих кастомных систем под конкурентным доступом”, а не строить новый технический слой — это прямо снимает Overengineering Risk, уже отмеченный в самой Epic Map (раздел 8).

### 6.9 PvP Arena (EPIC-011) и Rotational Retention Task (EPIC-012)

Технически обе фичи дешёвы и не меняют оценку — EPIC-011 тривиально надстраивается поверх готовых EPIC-002/003/010; EPIC-012 переиспользует EPIC-001/006. PRODUCT ISSUE (не решаю): ревью Game Designer’а (находки 2.5, 2.6) и сама Epic Map (раздел 8, “Замеченное противоречие”) уже корректно указывают на слабое/устаревшее обоснование обоих — это вопрос приоритезации для PM/Founder, техническая сложность здесь не является ограничивающим фактором в любую сторону.

## 7. Data Architecture

Player Persistent Data (player NBT/capabilities, без внешней БД): состояние дерева способностей, weapon instances, гир, статы, трофеи/валюта, survival-прогресс (голод/ресурсы, если кастом).

World Data: структуры/POI региона (EPIC-001), точки спавна кастомных мобов, состояние производственных цепочек (кастомное или делегированное Create/Mekanism).

Config/Content (data-driven, датапак-совместимо где возможно): архетипы оружия, статы мобов, узлы дерева способностей, loot-таблицы, item-описания лора — чтобы дизайнеры могли итерировать баланс без пересборки мода.

Runtime data: фазы боевого state machine, буферы client-side prediction, активные риск-транзакции (§6.6).

## 12. Technical Prototypes / Spikes

Spike 1 — Combat Network Sync (H6, уже задан в Epic Map, здесь — точный технический scope). Question: держится ли hit-confirmation и репликация пойз-состояния без критичных рассинхронизаций при реалистичном пинге на 2–4 игроках? Why it matters: go/no-go для всей боевой архитектуры. What to test: client-side prediction + server reconciliation конкретно для боевых окон и переходов пойза. Minimal implementation: минимальный прототип боя (одна атака, один тип моба, 2–4 клиента) под искусственной задержкой сети.

Prerequisite, не закрытый ни в одном документе: формулировка “нет критичных desync-инцидентов в согласованном пороге” ссылается на порог, который нигде фактически не согласован — ни числового значения, ни сценарного критерия не зафиксировано. Без этого результат спайка невозможно объективно проверить (что считать success, а что failure — по факту решается постфактум, “на глаз”). Это должен закрыть сам Tech Lead вместе с инженером, который физически будет проводить спайк — до его старта, а не после. Порог должен быть либо числовым (например: максимально допустимая частота/доля desync-инцидентов на N минут боя при заданном P95 ping), либо явным сценарным критерием (например: X из Y тестовых боёв на 2–4 клиентах проходят без рассинхронизации, ощутимой игроком), либо комбинацией. Открытый action item — см. §23.

Timebox: до старта контентного продакшена, приоритет №1. Decision after test: go/no-go на текущую боевую архитектуру, по фактически зафиксированному порогу.

Spike 2 — Совместимость Create/Mekanism/AE2 с кастомным боевым модом + TPS. Question: не конфликтуют ли глубокие хуки боевого мода (attack pipeline) с мод-экосистемой производственных цепочек; какова TPS-нагрузка при одновременном бое и активном производстве? Why it matters: определяет архитектуру EPIC-006 (кастом vs готовые моды) и общий performance-бюджет сессии. What to test: тестовая сборка со всеми модами одновременно, синтетическая нагрузка (активный бой + активные машины/kinetic-контрапшены). Minimal implementation: минимальная тестовая среда, не полноценный контент. Success: нет mixin-конфликтов, TPS в приемлемых пределах при целевой нагрузке (числа — NEEDS BENCHMARK, порог задаёт команда). Failure: конфликт → кастомная реализация survival вместо интеграции, или ограничение состава тяжёлых модов. Timebox: до Feature-декомпозиции EPIC-006. Decision after test: архитектурное решение по EPIC-006.

Spike 3 — Failure-state транзакционный механизм (только Tier A, см. §6.6). Question: можно ли реализовать snapshot/commit/rollback для риск-событий как независимый от контента компонент? Why it matters: закрывает HIGH RISK зону (потеря прогресса/дюп) для Tier A-семейства решений (rollback/outright loss), независимо от точного значения потери. What to test: механизм на синтетическом сценарии (искусственное “риск-событие” без финального дизайна). Success: транзакция атомарна, откат корректен, дисконнект посреди события не приводит к рассинхронизации данных. Timebox: параллельно с Combat Foundation. Decision after test: готовый Tier A-компонент, ожидающий подключения конкретной “что теряется”-логики от Design.

Явная граница scope: этот спайк валидирует только Tier A. Если Founder/Design выберут Tier B (bloodstain-style recoverable drop — персистентный world-object в точке смерти, TTL, конкурентный доступ в коопе, см. §6.6), результат Spike 3 его НЕ покрывает: потребуется отдельная оценка и, вероятно, отдельный технический спайк на recoverable-world-object подсистему. Успешный Spike 3 не означает готовность к Tier B.

Spike 4 (лёгкий) — FTB Teams как основа EPIC-009. Question: закрывает ли FTB Teams технические нужды “минимальных допусков” на 2–4 игроках? Why it matters: потенциально исключает написание permission-системы с нуля. What to test: конфигурация FTB Teams под гипотетические сценарии (делёж лута, право сноса построек). Timebox: короткий, низкий приоритет — после ответа Founder на вопрос “что вообще регулируем” (см. DESIGN ISSUE в §6.7).

## 13. Performance Risks

TPS-нагрузка при одновременном боссфайте и активных производственных цепочках — NEEDS BENCHMARK. Chunk loading/количество сущностей при 2–4 игроках, исследующих/сражающихся одновременно в регионе, — NEEDS BENCHMARK после построения региона. Client FPS от кастомных анимаций weapon arts — зависит от бюджета арт-ассетов (Unknown, не следует из документов). Частота сетевых пакетов боевого состояния на кооп-масштабе — вероятно в порядке нормы для vanilla-совместимого протокола, но тайминг-чувствительный hit-confirmation может потребовать кастомной lag-компенсации — часть Spike 1.

## 14. Multiplayer Risks

Server authority обязателен для урона/пойза/стамины — стандартная практика, не предмет дискуссии. Конкурентный доступ к survival-состоянию (ресурсные ноды, производственные цепочки) при 2–4 игроках нуждается в проверке, особенно в сочетании с кастомными боевыми хуками (Needs Investigation, часть Spike 2). Reconnect-сценарии посреди боя/крафта не описаны ни в одном документе — Open Technical Question, требует решения (см. §23).

Singleplayer-safe: боевой state machine, стамина/пойз, survival-механики (explicitly должны работать соло — подтверждено Product Definition, раздел 12). Multiplayer-critical: сетевая синхронизация боя (EPIC-003), корректность concurrent-доступа (EPIC-010).

## 15. Persistence & Migration

Player build/прогрессия/weapon instances/гир/трофеи/валюта/survival-состояние — через player NBT/capability слой NeoForge, без внешней БД. Мировые структуры — стандартный world save. Schema versioning: полноценная migration-система не нужна на этом этапе (принцип “не переинжиниринг”), но с первого дня рекомендую версионировать персистентные структуры игрока простым полем версии + функцией-заглушкой миграции — иначе изменения баланса/данных во время самой разработки будут ломать сохранения плейтестеров. Acceptable for MVP: простое версионирование. Post-MVP: полноценная migration-стратегия, когда/если начнётся серверное направление.

## 16. QA Technical Handoff

Высокий приоритет тестирования: hit-confirmation под реальным пингом (2–4 игрока); desync пойз-состояния; корректность failure-state транзакций (HIGH RISK — потеря прогресса/дюп); конкурентный доступ к survival-ресурсам; баланс боссового энкаунтера по всем 5–8 билдам. Регрессионный риск: любое изменение модели WeaponArchetype одновременно влияет на ощущение боя (EPIC-002) и прогрессию (EPIC-005) — нужно совместное тестовое покрытие.

## 17. Analytics Technical Handoff

Технически доступные для сбора события (не продуктовые метрики — только техническая возможность): combat_hit, poise_break, player_death (с причиной), trophy_collected, gear_upgraded, build_selected, resource_gathered, desync_incident, session_start/end (server-side); lore_item_viewed, build_screen_interaction (client-side, сигнал для H7/H2).

## 18. Observability

Минимально достаточный уровень: server-side логирование отказов валидации боя (сигнал desync/потенциального чита), crash reporting, admin-команды для отладки спавна мобов и survival-состояния. Enterprise-уровень observability не нужен на масштабе MVP/малой команды.

## 19. Security / Exploit Risks

Server-authoritative расчёт урона/пойза/стамины — обязателен, не предмет компромисса даже на MVP. Базовая защита от дублирования трофеев/гира при апгрейде — рекомендую внедрить как Acceptable for MVP минимум, отдельно от полноценного анти-дюп-бэкенда, который explicitly вне MVP (Product Definition, раздел 12): это разные уровни защиты — “не потерять данные при обычном использовании” не равно “защита от намеренной экономической эксплуатации в постоянной экономике”. Отсутствие персистентной экономики в MVP уже само по себе радикально снижает exploit-поверхность.

## 20. Technical Debt

Acceptable for MVP: отсутствие полноценного анти-дюпа; версионирование данных вместо полной migration-системы; минимальная observability; потенциально полная передача survival-логики в Create/Mekanism/AE2 вместо кастома (снижает контроль, экономит месяцы разработки — конкретный trade-off, зависит от Spike 2).

Must Fix Before MVP: server-authoritative валидация боя; базовые guard’ы от дублирования трофеев/гира.

Post-MVP Technical Debt: полная migration-стратегия; полноценная observability; анти-дюп/экономический бэкенд; сетевая архитектура для постоянного сервера (иные характеристики масштабирования, чем кооп-сцена).

Architectural Risk: если EPIC-006 в итоге строится как глубокая кастомная интеграция с внутренностями Create/Mekanism, а не через их API/интерфейсы, — этот риск компаундируется при переходе к серверному направлению (иные допущения о владении состоянием). Флагирую для пересмотра именно в момент этого перехода, не сейчас.

## 23. Open Technical Questions

Blocking: защитный инструмент боя (DESIGN ISSUE, передано Founder/Game Design, см. Product Definition раздел 19.20) — блокирует только DefensiveToolSystem, не весь EPIC-002; итог Spike 1 (сетевой спайк) — go/no-go для H6.

| Failure-state механика не определена | High — core loop непроверяем как risk/reward система; если Design выберет Tier B (bloodstain-style), появится дополнительный, ещё не оценённый технический объём (см. §6.6) | Certain на сегодня | Design-решение (DESIGN ISSUE) + параллельная разработка Tier A транзакционного механизма (Spike 3); Tier B (если выбран) — отдельная оценка и спайк после решения |

## FINAL TECHNICAL GATE

NEEDS PROTOTYPE — для боевого/сетевого ядра (Spike 1, старт которого требует сначала зафиксировать порог success/failure) и архитектуры survival-системы (Spike 2); оба должны быть пройдены до масштабирования контента поверх непроверенного технического основания, как справедливо отмечает и сам Product Definition (раздел, “Critical blockers — нет… но обе развилки способны изменить MVP по существу”).

TECHNICALLY READY WITH RISKS — для Foundation-слоя, Combat Foundation, content-треков (EPIC-001/007) и большей части декомпозиции при условии принятия предложенных в этом документе технических решений (§22) и закрытия одного design-блокера (защитный инструмент боя) и одного product-вопроса (что именно теряется при неудаче — §6.6).
