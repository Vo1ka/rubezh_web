## 1. CONFLICT DETECTED — README/ТЗ прямо противоречит уже принятому и реализованному решению D-38/D-39

**Источник A (README/ТЗ репозитория, раздел «За пределами этого ТЗ»):** «Ни авторские боссы, ни интеграция любых сторонних модов, кроме Better Combat... не входят в объём этой работы — не как отложенный этап того же плана, а как принципиально другая задача... Если команда решит расширяться в эту сторону, это отдельное ТЗ».

**Источник B (коммит `31c81c5`, 29.09, «Add public API for external mob, boss and loot mods», подтверждён владельцем по D-38/D-39):** построен, закоммичен и задокументирован (`docs/api/external-mods.md`) полноценный публичный контракт `RubezhApi` + data map `rubezh:combatants` + 4 события именно для того, чтобы мобы/боссы/лут приходили из **сторонних модов**.

Это не мелкое расхождение — это ровно тот сценарий, о котором предупреждает документ, который я готовил 17.09 (два девкита под разными именами): один документ говорит «не делаем», код говорит «уже сделали». Владелец (вы) принял архитектурное решение, но README, который держит на себе Sprint-структуру и объём ТЗ, не переписан.

**Impact:** любой разработчик, открывший README сегодня, спланирует контент-этап неправильно — будет либо ждать «отдельного проекта» для мобов, который на самом деле уже стартовал, либо не будет знать, что граница ответственности сдвинулась.

**Required Decision:** обновить README/ТЗ репозитория (раздел «За пределами этого ТЗ» и раздел 1 «Три зоны ответственности» — таблица Инженера В теперь должна включать курирование внешних мод-мобов, а не только авторинг оружия/скиллов). Это TechLead-уровня правка (меняет объявленный scope документа), но по содержанию — просто синхронизация текста с уже принятым решением, не новое архитектурное решение. Рекомендую: 30 минут, TechLead подтверждает формулировку, кто-то из команды правит README одним PR.

## 4. Развернутый ответ на ваш вопрос: что реально идёт к TechLead

Не весь контент-этап. Конкретно два пункта:

1. **AN-01** — состояние анимационного конвейера. Это архитектурный вопрос (HOW), не организационный.
2. **Синхронизация README/ТЗ с D-38/D-39** (раздел 1 этого документа) — формально тоже TechLead, потому что README — часть утверждённой технической документации, а не моя зона для самостоятельной правки.

Всё остальное — M-04 (множители босса) и решение по MVP-подветкам (T-01 зависимость) — это **Game Design/Product**, не TechLead: числа баланса и объём контента, не архитектура. M-01–M-03, W-01–W-04, S-01, T-01–T-03 — это исполнение, для которого я и есть Development Lead; TechLead здесь не нужен, если только в процессе не всплывёт архитектурная невозможность.

| Роль | Кто (по репозиторию) | Основная нагрузка в контент-фазе |
|---|---|---|
| Systems Developer | Инженер А | Основная работа уже сделана (баланс-математика). В контент-фазе — на подхвате: property-тесты под новый контент (W-01…S-01), не полноценная загрузка |
| Minecraft Mod Developer | Инженер Б | M-01 (живая проверка D-39), AN-01 (вместе с TechLead), затем на подхвате под W/S/T |
| Content/Integration Developer | Инженер В | Основная нагрузка контент-фазы: W-01…W-04, S-01, T-01, M-03 — это явно больше, чем один человек тянет параллельно, см. критический путь ниже |

**Явный риск, не скрываю:** вся содержательная контент-работа (оружие, заклинания, дерево, datapack-записи мобов) ложится на одного человека (Инженер В) по текущей структуре команды. Это не проблема архитектуры — это ограничение состава команды (§14 моей инструкции: команда из 3 разработчиков, не 10). Стоит явно решить с вами: либо это принимается как есть (контент-фаза займёт кратно дольше combat-core фазы), либо кто-то временно переключается с A/Б на контент-авторинг.
